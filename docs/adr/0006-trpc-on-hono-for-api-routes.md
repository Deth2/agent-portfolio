# tRPC su Hono invece di Route Handler Next.js "nudi"

L'endpoint chat era inizialmente un singolo Route Handler Next.js (`app/api/chat/route.ts`) che parsava il body a mano e validava i campi manualmente. Per uniformare come le API di questo progetto vengono definite e validate man mano che se ne aggiungono altre, adottiamo **tRPC servito su Hono**: un unico Route Handler catch-all (`app/api/[[...route]]/route.ts`) delega tutto `/api/*` a un'app Hono (`src/server/hono.ts`), che monta i router tRPC (`src/server/routers`) tramite `@hono/trpc-server`. I procedure tRPC validano l'input con Zod e restituiscono tipi end-to-end senza generazione di client separata; sul client, il chiamante è **TanStack Query** (`@trpc/tanstack-react-query`): `useTRPC()` (`src/lib/trpc/context.ts`) espone le procedure come opzioni per `useQuery`/`useMutation`, montate sotto un `QueryClientProvider` unico per tutta l'app (`src/lib/trpc/provider.tsx`, in `layout.tsx`). `useChatSession` continua a possedere la history dei messaggi e il contatore del Question Limit; la chiamata di rete vera e propria (stato pending/errore incluso) è della mutation TanStack Query, incapsulata da `useAskAboutCv` (`src/lib/chat/use-ask-about-cv.ts`) nella forma `AskAboutCv` che `useChatSession` si aspetta. Hono resta il punto in cui aggiungere in futuro rotte non-tRPC (webhook, health check) senza spargere altri Route Handler ad-hoc in `app/api`.

**Esito**: `chat.ask` è l'unica procedure oggi, sostituisce l'handler POST precedente 1:1 (stesso `askAboutCv`, stesso `mockCv` come CV Profile fino a quando il Markdown reale non esiste — vedi [ADR-0003](0003-openai-compatible-llm-adapter.md)).

Costo accettato: più codice di infrastruttura (Hono + adapter tRPC) per un solo endpoint oggi, a fronte di validazione tipata e di un pattern che scala meglio se il numero di endpoint cresce. Drizzle (o un altro layer di persistenza) non è stato introdotto: il progetto non ha ancora alcun dato che richieda un database — la CV Profile è un file Markdown letto a build/request time, e il Question Limit è puramente client-side (vedi [ADR-0002](0002-client-side-question-limit.md)). Va aggiunto insieme a un router tRPC dedicato solo quando emergerà un bisogno reale di stato persistente lato server.
